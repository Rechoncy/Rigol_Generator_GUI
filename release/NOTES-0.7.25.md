日期：2026-10-29。状态：按用户本次“发布到 GitHub”要求正式发行 [v0.7.25](https://github.com/Rechoncy/Rigol_Generator_GUI/releases/tag/v0.7.25)。标签发布流程从本次文档提交重新构建、验证并发布，实际结果以对应工作流及正式 `release-manifest.json` 为准，不预写新标签产物验收成功。

正式附件本地副本使用 `dist/published/v0.7.25/`；原 `dist/local/v0.7.25/` 候选（源码提交 `47884b2`）与 v0.7.24 正式附件保留，不覆盖已经交付的文件。前期源码、候选构建与正式标签构建分别记录，不能用候选结果替代正式产物验证。

## 问题与原因

用户反馈安装后检查更新提示“GitHub 暂时限制请求”。首次使用 urllib 的只读诊断中，匿名 Release API 返回 HTTP 403，`X-RateLimit-Remaining: 0`；同仓库的官方 `releases/latest/download/release-manifest.json` 返回 200，内容为正式 v0.7.24。随后以真实 v0.7.24 源码的 Qt 更新检查器实测，API 返回 200、剩余额度为 58。两种结果提示代理/网络路径或限流状态可能不同，不能把 urllib 的 403 等同于用户安装环境已被完整复现。

GitHub 的匿名 REST API 额度按出口 IP 计算，每小时 60 次；共享校园/单位网络、代理出口上的其他程序也会使用同一额度。软件原有自动检查为启动约 3 秒一次、运行中每 6 小时一次，没有发现自动请求风暴；但失败后没有退避，反复手动检查会继续发请求。原版还把所有 HTTP 403 一律称为限流，无法区分代理或访问策略拒绝。规则见 [GitHub API 额度说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。

## 修复范围

- API 限流时尝试同一仓库的官方最新发行清单，保留正式版本比较及规范附件的大小、SHA-256 校验，安装版仍选择 Setup，便携格式仍选择原有对应附件。官方固定附件入口见 [GitHub 发行链接说明](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)。
- 备用检查限定官方 HTTPS 地址、项目路径、正式版本与受限跳转，限制响应大小和总检查时间；无效或不匹配的清单不能触发下载与安装，不从网页内容执行命令。
- 按 `Retry-After`/`X-RateLimit-Reset` 安排 API 重试等待；成功结果缓存 60 秒，失败后冷却 30 秒，避免重复点击继续消耗额度。这些状态仅在当前进程内存中，不写入用户数据。普通访问拒绝、网络/证书错误与限流分别提示；仍使用本机系统代理，不修改全局代理。
- 首次检查失败也可打开本仓库固定发布页，不要求先成功发现新版。
- 重复或缓存的同版通知保留已校验 Setup 和等待设备空闲的安装；安装请求失败后重新检查不自动重放，仍可显式点击“安装更新”重试。
- 不要求用户登录或提供访问令牌，不在程序中内置令牌；不上传设备地址、配置或实验数据。联网检查与仪器队列、扫描、采集和停止清理保持独立。

## 旧版获得修复

v0.7.24 及更早程序不含上述备用检查。正式 v0.7.25 可被旧更新器检测并提供适用附件；若旧版已因限流无法发现更新，则需等待 GitHub 额度恢复，或从本次 Release 手动下载并运行 `Lab-Control-Center-0.7.25-windows-x64-setup.exe`。旧程序不能在尚未安装修复时自动拥有备用检查逻辑。手动运行前先停止任务并正常退出旧程序，安装时沿用已有用户数据目录。无需先手动删除程序或用户数据；安装器仍先备份数据，再卸载已登记旧版、安装新版并核对恢复。

本轮不更改用户数据格式、仪器协议或安装数据恢复规则。已有下载的大小与 SHA-256 校验继续执行，缺少有效附件或校验信息时保留发布页入口，不能自动下载或安装。
